## Findings

### P1-1 — placeOrders `PROCESSED_WITH_ERRORS`/`FAILURE` con report non-FAILURE chiuso FAILED definitivo (fail-open)
- `betfair_client.py:1733-1738` (`if status != "SUCCESS": raise BET_FAILED ...`) prima del loop dei report (`:1740-1748`);
  `order_unknown` falso (`:1770-1777`). Doc che lo codifica: `docs/trading_engine_executor_contract.md:20` (riga «rifiuto dichiarato … `PROCESSED_WITH_ERRORS` … | FAILED | sì»).
- Scenario: Betfair risponde `{"status":"PROCESSED_WITH_ERRORS","errorCode":"ERROR_IN_ORDER","instructionReports":[{"status":"TIMEOUT"}]}`
  (o report `SUCCESS` con `betId`, o report senza status). Per Betfair PWE = «ordine accettato, almeno un'istruzione con errori»;
  un report TIMEOUT = esito ignoto. Oggi: `{"ok":False,"order_unknown":False}` → TradingEngine `DOWNSTREAM_SEMANTIC_FAILURE` → FAILED,
  rilascio di tavolo, riserva e chiave anti-duplicato con un ordine forse vivo (in un caso con betId noto). Stesso per `FAILURE` + report SUCCESS/betId (contraddittorio).
- Prova (probe `test_probe_A_client` / `test_probe_A_engine`, 4 corpi × 2 livelli = 8 FAIL sul head): es.
  `pwe_report_timeout: FAILED DOWNSTREAM_SEMANTIC_FAILURE:{'ok': False, 'error': 'BET_FAILED: PROCESSED_WITH_ERRORS ERROR_IN_ORDER', ..., 'order_unknown': False}`.
- Origine: preesistente su main (stesso ramo `status != "SUCCESS"`), ma ricade esattamente nella promessa F-14 e il PR lo rende normativo nella doc.
- Fix: con status `FAILURE`/`PROCESSED_WITH_ERRORS`, se esiste almeno un report con status ≠ `FAILURE` (SUCCESS/PLACED, TIMEOUT, assente, sconosciuto)
  → `BET_REPORT_STATUS_UNRECOGNIZED` (o codice dedicato in `_RISPOSTA_ILLEGGIBILE_DOPO_L_INVIO`) ⇒ order_unknown + `result` conservato;
  restano FAILED solo: FAILURE/PWE senza report, o con TUTTI i report FAILURE (il test esistente `processed_with_errors_report_failure` resta verde).
  Aggiornare la riga 20 della doc. Test RED/GREEN: i 4 corpi del probe A.

### P2-1 — cancel di tutto il mercato (bet_ids vuoto): report `TIMEOUT` ignorato
- `betfair_client.py:1855-1880` (`_cancel_result`): con `requested == []` i report TIMEOUT/sconosciuti non entrano in `missing`.
  `status SUCCESS` + report `[SUCCESS(1), TIMEOUT(2)]` ⇒ `outcome SUCCESS, ok True` (probe `test_probe_C_cancel_all_timeout_report`).
  `PWE` + solo report TIMEOUT ⇒ `outcome FAILED` invece di AMBIGUOUS (probe C2); la doc §2-bis dice FAILED solo con «tutti i report FAILURE».
- Impatto: `emergency_stop` (`core/runtime_controller.py:2301-2312`) registra ok=True / cancelled su un mercato con un ordine forse vivo
  (solo reporting: lo stato trading non viene liberato da qui). Fix: raccogliere `unknown` (report non SUCCESS/FAILURE) e trattarli come `missing`
  anche senza `requested`; `FAILED` solo se tutti i report sono FAILURE.
