### Protezione del runtime lock

core/runtime_controller.py:_acquire_runtime_instance_lock apre '<realpath(db)>.runtime.lock' in 'a+' e prende fcntl.flock(LOCK_EX|LOCK_NB) (Linux) o msvcrt.locking(LK_NBLCK, byte 0) (Windows); il descrittore resta in self._instance_lock_fh per tutta la vita del runtime. _release_runtime_instance_lock_if_stopped chiude il descrittore solo con mode STOPPED e senza smontaggio pendente; _teardown_failed_start smonta i servizi di uno start fallito e trattiene il lock se lo smontaggio fallisce; start/stop serializzati da _runtime_lifecycle_lock. Non esiste alcun controllo periodico dell'identita' del file (nessun confronto fstat/stat dell'inode, nessun watchdog, nessun contenuto/PID/fencing scritto nel file). Se .runtime.lock viene cancellato a runtime attivo: su Linux l'unlink rimuove la voce di directory ma il flock resta sull'inode orfano tenuto aperto dal primo processo; un secondo runtime fa open('a+') creando un NUOVO file/inode allo stesso percorso, il flock su di esso riesce (nessun contendente) e _acquire_runtime_instance_lock restituisce '' => il secondo runtime parte sullo stesso database, senza alcun evento RUNTIME_START_REFUSED; il primo runtime non se ne accorge e al suo stop chiude il proprio descrittore senza toccare il nuovo file. Su Windows la cancellazione di un file aperto da Python (senza FILE_SHARE_DELETE) e' normalmente rifiutata dal sistema, quindi il bypass per cancellazione non e' riproducibile allo stesso modo, ma non esiste nemmeno li' una verifica attiva. Test esistenti: tests/acceptance/test_issue461_pr29c_settlement_processes_and_schema.py (21 passed: due processi OS, crash libera il DB, grafie diverse, byte 0 Windows) — NESSUN test copre la cancellazione del file a runtime attivo. Stato: PARZIALE/BLOCCATO — decisione owner 22/10 (c.6335409948): threat model, riproduzione e mitigazione robusta (ownership/fencing/OS-level) con test cross-process obbligatori prima di qualunque certificazione LIVE; nessuna PR assegnata (candidata PR32).
